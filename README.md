# ระบบจองสถานีชาร์จ EV (EV Charging Station Booking System)

โปรแกรม CLI บนเทอร์มินัล สำหรับวิชา **Python File I/O** — เน้นการอ่าน/เขียน
ไฟล์ไบนารีแบบ **fixed-length record** ด้วยโมดูล `struct`
(ใช้เฉพาะ **Python Standard Library** ไม่ต้องติดตั้งไลบรารีภายนอก)

---

## 1. วิธีรันโปรแกรม

ต้องใช้ **Python 3.10 ขึ้นไป** (ทดสอบแล้วบน Python 3.13)

```bash
# 1) เข้าเมนูหลัก (เริ่มจากฐานข้อมูลว่าง)
python main.py

# 2) สร้างข้อมูลตัวอย่าง 55 ระเบียก แล้วเข้าเมนู
python main.py --seed

# 3) สร้างรายงาน .txt จากข้อมูลปัจจุบัน แล้วออก
python main.py --report-only

# 4) สร้าง index.dat ใหม่จาก charge_points.log (ซ่อมดัชนี)
python main.py --rebuild-index

# 5) เริ่มระบบใหม่แบบว่างเปล่า
python main.py --reset

# 6) ใช้โฟลเดอร์เก็บข้อมูลอื่น
python main.py --data-dir D:\my-ev-data

# 7) ดูสเปกระเบียนของไฟล์ไบนารีทั้ง 3 ไฟล์
python main.py --spec

# 8) สร้างข้อมูลตัวอย่าง (รัน seed_data.py โดยตรงก็ได้)
python seed_data.py --force
```

รันชุดทดสอบ:

```bash
python -m unittest discover -s tests -v      # ทั้งหมด 183 เทสต์
python -m unittest tests.test_models -v       # เทสต์เฉพาะโมดูล
```

> **หมายเหตุ:** ถ้าใช้ Windows Terminal แล้วภาษาไทยแสดงเป็นตัวยึกยือ ให้ตั้งค่า
> code page เป็น UTF-8 ก่อนด้วยคำสั่ง `chcp 65001` (ไฟล์ทั้งหมดถูกเขียนเป็น
> UTF-8 อยู่แล้ว เพียงแต่ console แสดงผลไม่ถูก)

## 3. ตารางสเปกระเบียนทั้ง 3 ไฟล์

ทุกไฟล์กำหนด **endianness เป็น Little-Endian (`<`)** และใช้ระเบียนความยาวคงที่
(สตริงเข้ารหัด UTF-8 เติมด้วย `\x00` ให้ครบ และตัดโดยไม่ตัดกลางอักขระ UTF-8)

### 3.1 `charge_points.dat` — struct `<l10s30s10sfflllll` = **82 ไบต์**

| # | ฟิลด์ | ชนิด | ขนาด | ความหมาย |
|---|-------|------|------|----------|
| 1 | `point_id` | `l` | 4 | รหัสหัวชาร์จ (Primary Key ห้ามซ้ำ) |
| 2 | `station_code` | `10s` | 10 | เช่น `EVS-0001` |
| 3 | `location` | `30s` | 30 | เช่น "สยามพารากอน ชั้น B1" |
| 4 | `plug_type` | `10s` | 10 | `Type2` / `CCS2` / `CHAdeMO` / `GB-T` |
| 5 | `power_kw` | `f` | 4 | กำลังไฟสูงสุด (kW) |
| 6 | `price_per_kwh` | `f` | 4 | ราคา (THB/kWh) |
| 7 | `status` | `l` | 4 | 1 = Active, 0 = Inactive (ปิดซ่อมบำรุง) |
| 8 | `is_booked` | `l` | 4 | 1 = มีการจอง/กำลังชาร์จ, 0 = ว่าง |
| 9 | `is_deleted` | `l` | 4 | 1 = ถูกลบ (soft delete), 0 = ปกติ |
| 10 | `created_at` | `l` | 4 | Unix timestamp |
| 11 | `updated_at` | `l` | 4 | Unix timestamp |

รวม: 4 + 10 + 30 + 10 + 4 + 4 + 4 + 4 + 4 + 4 + 4 = **82 ไบต์**

### 3.2 `charge_points.log` — struct `<lllllf` = **24 ไบต์**

| # | ฟิลด์ | ชนิด | ขนาด | ความหมาย |
|---|-------|------|------|----------|
| 1 | `ts` | `l` | 4 | Unix timestamp ของเหตุการณ์ |
| 2 | `op_code` | `l` | 4 | 1=ADD, 2=UPDATE, 3=DELETE, 4=VIEW |
| 3 | `point_id` | `l` | 4 | รหัสหัวชาร์จที่เกี่ยวข้อง |
| 4 | `status_after` | `l` | 4 | สถานะหลังเหตุการณ์ |
| 5 | `is_booked_after` | `l` | 4 | สถานะการจองหลังเหตุการณ์ |
| 6 | `price_after_thb` | `f` | 4 | ราคาหลังเหตุการณ์ (THB/kWh) |

รวม: 5×4 + 4 = **24 ไบต์**

> **หมายเหตุเรื่องรูปแบบ struct:** เอกสารโจทย์เขียนไว้ว่า `<llllfl` แต่เมื่อพิจารณา
> **ลำดับฟิลด์จริง** ที่ระบุไว้ (5 ฟิลด์แรกเป็น long และตัวสุดท้ายเป็น float)
> รูปแบบที่ถูกต้องจึงเป็น **`<lllllf`** ซึ่งให้ขนาดเท่ากันคือ 24 ไบต์
> (มีคำอธิบายกำกับอยู่ใน `models.py` และทดสอบยืนยันลำดับฟิลด์ใน `tests/test_models.py`)

### 3.3 `index.dat` — struct `<ll` = **8 ไบต์**

| # | ฟิลด์ | ชนิด | ขนาด | ความหมาย |
|---|-------|------|------|----------|
| 1 | `point_id` | `l` | 4 | รหัสหัวชาร์จ |
| 2 | `log_seq` | `l` | 4 | ลำดับ (เริ่มที่ 0) ของเหตุการณ์ล่าสุดใน log |

รวม: 4 + 4 = **8 ไบต์**

ใช้คำนวณตำแหน่งใน log ได้ทันที: `offset = log_seq * 24`
จึงค้นประวัติล่าสุดของหัวชาร์จได้โดยไม่ต้องไล่อ่าน log ทั้งไฟล์

## 4. เมนูการใช้งาน

```
1) Add (เพิ่ม)
2) Update (แก้ไข)
3) Delete (ลบแบบ soft delete)
4) View (ดู)
   4.1 ดูรายการเดียว (ตาม point_id) + ประวัติล่าสุดผ่าน index.dat
   4.2 ดูทั้งหมด (รวมระเบียกที่ถูกลบแล้ว)
   4.3 ดูแบบกรอง (station_code / plug_type / status / is_booked)
   4.4 สถิติโดยสรุป
5) Generate Report (.txt)
0) Exit (สร้างรายงานอัตโนมัติ + flush + os.fsync)
```

**กติกาสำคัญของแต่ละเมนู**

| เมนู | พฤติกรรม |
|------|----------|
| **Add** | ตรวจ `point_id` ซ้ำ → ใช้ช่องว่างที่เคยถูกลบก่อน → ไม่มีช่องว่างจึงต่อท้ายไฟล์ · ตั้ง `created_at`/`updated_at` = เวลาปัจจุบัน · เขียน log (op=1) · อัปเดต index |
| **Update** | แก้ได้ทุกฟิลด์ **ยกเว้น** `point_id` และ `created_at` · สลับ `status` / `is_booked` ได้ · อัปเดต `updated_at` · เขียนทับระเบียกเดิมด้วย `seek` · log (op=2) |
| **Delete** | soft delete (ตั้ง `is_deleted=1`) · **ต้องยืนยัน y/n** ก่อน · **ห้ามลบหัวที่ `is_booked=1`** · log (op=3) |
| **View 4.1** | เขียน log (op=4) · แสดงประวัติล่าสุดโดยอ่านผ่าน `index.dat` |
| **View 4.2** | แสดงระเบียกทั้งหมด **รวมที่ถูกลบแล้ว** |
| **View 4.3/4.4** | ข้ามระเบียกที่ถูกลบ |

**การตรวจสอบอินพุต** — ถ้ากรอกผิดจะแจ้งเหตุผลและถามใหม่ (ไม่หยุดโปรแกรม)

* `point_id` ต้องเป็นจำนวนเต็มบวก
* `station_code` ต้องเป็น `EVS-NNNN`
* `plug_type` เลือกจาก Type2 / CCS2 / CHAdeMO / GB-T
* `power_kw` และ `price_per_kwh` ต้องมากกว่า 0
* `status` และ `is_booked` รับเฉพาะ 0 / 1
* `location` ห้ามว่าง และไม่เกิน 30 ไบต์ (UTF-8) — เกินจะ**เตือนก่อนตัด**
* รองรับ `ValueError`, `EOFError` (ปิด stdin) และ `KeyboardInterrupt` (Ctrl+C)

**การตรวจไฟล์ตอนเริ่มโปรแกรม**

1. ขนาดไฟล์ไม่หารลงตัวด้วยขนาดระเบียก → แจ้งเตือนและตัดส่วนเกินทิ้ง
2. `index.dat` ไม่ตรงกับ log → สร้างดัชนีใหม่จาก log อัตโนมัติ
   (หรือสั่งด้วยตนเองด้วย `python main.py --rebuild-index`)

## 6. สรุปการตัดสินใจและข้อสมมติฐาน

### 6.1 การตัดสินใจในการออกแบบ

**1) วิธีทำ free-list (นำช่องที่ลบแล้วกลับมาใช้ซ้ำ)**

เลือกแนวทาง **"soft delete + เก็บรายการ slot ที่ว่างไว้ในหน่วยความจำ"**

* ตอนเริ่มโปรแกรมสแกนไฟล์ทั้งไฟล์ด้วย `refresh_free_slots()` เพื่อรวบรวม
  slot index ที่ `is_deleted=1` เก็บไว้ในลิสต์ `store.free_slots`
* เวลา `Add` ใหม่ ระบบเลือกช่องว่างช่องแรกในลิสต์ → เขียนทับด้วย `seek` + `write`
  (ไม่ต่อท้ายไฟล์ จึงไม่ขยายไฟล์โดยไม่จำเป็น)
* **เหตุผลที่ไม่ลบไบต์จริง:** ต้องคงลำดับระเบียกให้นิ่ง เพราะ `log_seq`
  ใน `index.dat` และตำแหน่งใน `charge_points.log` อ้างอิงด้วยลำดับ (offset)
  ถ้าลบไบต์ออกกลาง ๆ ตำแหน่งทั้งหมดหลังจากนั้นจะเลื่อนทั้งหมด ทำให้
  ประวัติทั้งหมดผิดความหมาย

**2) การจัดการ "ระเบียกซ้ำ" ใน index.dat**

* กติกา **1 point_id = 1 ระเบียก**: คลาส `PointIndex` แคชตำแหน่งของแต่ละ
  `point_id` ไว้ใน `_slot_by_id` เมื่ออัปเดตก็จะ `seek` ไปทับระเบียกเดิม
  เสมอ (ไม่ต่อท้ายไฟล์) จึงไม่เกิดระเบียกซ้ำแม้อัปเดตกี่ครั้งก็ตาม
* หากไฟล์มีระเบียกซ้ำอยู่แล้ว (จากไฟล์เสีย) ตอนโหลดจะเก็บค่าจากระเบียกที่
  `log_seq` มากที่สุด ซึ่งสอดคล้องกับตรรกะ "อัปเดตทับค่าเดิม"
* มี `verify_against_log()` ตรวจความสอดคล้อง และ `rebuild()` สร้างใหม่จาก log ได้
  โดยเลือก `seq` ล่าสุดของแต่ละ `point_id`

**3) ชั้นบริการ (service layer) แยกจากเมนู**

`main.py` แยกตรรกะ CRUD ออกเป็น `add_record` / `update_record` / `delete_record` /
`view_record` ซึ่ง **ไม่โต้ตอบผู้ใช้** ส่วนเมนู `add_point` / `update_point` /
`delete_point` ทำหน้าที่รับค่าจากผู้ใช้แล้วส่งต่อไปยังชั้นบริการ
ทำให้ (1) ไม่มีตรรกะซ้ำซ้อน และ (2) ทดสอบ CRUD ได้โดยไม่ต้องจำลอง stdin

**4) เวลาในรายงานใช้เขตเวลา +07:00 เสมอ**

กำหนด `THAI_TZ = timezone(timedelta(hours=7))` แล้วแปลงด้วย
`datetime.fromtimestamp(ts, THAI_TZ)` จึงไม่ขึ้นกับเขตเวลาของเครื่องที่รัน

**5) ความกว้างตารางภาษาไทย: ใช้ทั้ง `combining()` และ `category()`**

ข้อกำหนดให้ใช้ `unicodedata.combining` แต่พบว่า **สระไทยบางตัวมี
`combining()` = 0** (เช่น "ั" U+0E31, "ิ" U+0E35) เพราะ Unicode จัดให้อยู่ในหมวด
`Mn` (Mark, nonspacing) ที่มี Combining_Class = 0 หากใช้ `combining()` อย่างเดียว
เส้นขอบตารางจะเบี้ยว จึงตรวจเพิ่ม `unicodedata.category(char) in ("Mn", "Me")`
ประกอบด้วย (รายละเอียดในคอมเมนต์ `_char_width()` และมีเทสต์รองรับ)

### รายการกรณีทดสอบเชิงลบที่ครอบคลุม

* `point_id` เป็น 0 / เลขติดลบ / ข้อความผิดประเภท
* `station_code` ผิดรูปแบบทุกกรณี (`EVS-001`, `EVS-00001`, `ABC-0001` ...)
* `plug_type` ไม่อยู่ในรายการ, `power_kw` / `price` ≤ 0 หรือไม่ใช่ตัวเลข
* `status` / `is_booked` นอกเหนือจาก 0/1
* `location` ว่าง และยาวเกิน 30 ไบต์ (ต้องเตือนและตัด)
* เพิ่ม `point_id` ซ้ำ, แก้ไข/ลบคีย์ที่ไม่มีอยู่, พยายามแก้ `point_id`/`created_at`

* ไฟล์ทั้ง 3 ไฟล์ที่ถูกตัดกลางระเบียก ต้องถูกตรวจจับและซ่อมแซมได้
* `index.dat` หาย / ชี้ค่าผิด ต้องสร้างใหม่จาก log ได้
